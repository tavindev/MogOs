# Phase 5: SMP, Threads and Fair Scheduling

Goal: several cores run threads of one process under a fair scheduler with resource groups. The locking model is fixed first, so every later shared table (page cache, network stack) is built on it. MogOs has no practical core cap (as many cores as QEMU `virt` offers: 512 under TCG, 64 under hvf) and no fixed object limits: an object is bounded by its owner's budget (Decided).

## Steps

Each done-when names its e2e test (a QEMU boot test in `crates/e2e/tests/boot.rs`; host unit tests only for tricky pure logic), the benchmarks it must hold and the ones it adds, and the invariants it keeps. Benchmarks are hvf medians of 21 interleaved boots against the step's base commit (`docs/BENCHMARKS.md`); "hold" means within noise, and a slowdown is a failure: removed, or shown unavoidable with numbers. The tracked kernel benchmarks are yield (`test=bench`, 70 ns), syscall (`test=bench-syscall`, 29 ns), pipe (`test=bench-pipe`, 374 ns) and boot (178 us without a disk); from step 25a they are measured at `-smp 1` and `-smp 4`, and from step 25c `test=bench-smp` adds throughput at 1, 2, 4, 8 and 12 cores. The e2e harness runs under TCG on a loaded host, so done-whens assert scheduler state and order, or a median of N samples under a loose ceiling, never a single wall-clock bound.

Step 25a (bring-up: `arch` boot, the secondary entry, per-core GIC and timer) runs in parallel with steps 26-27 (process/thread split and wait-on-address, one core). 25b (the scheduler per core) needs all three and rebases onto 26's process table; 25c (no core cap) follows 25b, and 28-32 follow in order.

| 25b | Scheduler per core | Idle contexts are per core, not scheduler slots (no slot or ASID spent): `Scheduler` keeps `current` per core, in a `Vec` sized from `Board::cpus` at boot (never `MAX_CPUS`, so step 25c leaves it alone), `advance(cpu)` returns the highest-priority ready task not running elsewhere, or none, and the board then resumes that core's idle frame, which loads the boot table (`set_ttbr0(boot_table, 0)`), so no core keeps walking a dead process's tables. | 26 | Threads | Process state moves out of the per-slot arrays into a process table in `kernel` (`Processes<P>`: address space, `Handles`, `Memory` with the budget and map cursor, live thread count, generation); a task slot keeps its frame, state, priorities and kernel stack, and names its process. | 27 | Wait-on-address with PI | New syscalls: `futex_wait(addr, expected, deadline)` blocks while the aligned `u32` at `addr` equals `expected` (read under the big lock, so a wake after a store is never lost; `deadline` in counter ticks, 0 for none, else `ETIMEDOUT`); `futex_wake(addr, n)` wakes up to `n` waiters, highest priority first, and returns the count; `futex_lock(addr)` / `futex_unlock(addr)` are the PI pair: the word holds the owner's thread id (0 when free; slot plus generation in the bits below the waiters bit, so an id never names a later thread), the uncontended path is a CAS in user space, and contended the kernel sets the waiters bit with an `arch` CAS on the user word (probed like `user_bytes_mut`), boosts the owner through `effective`, and `futex_unlock` hands the lock to the highest-priority waiter and `unboost`s; `EDEADLK` for the owner. The owner id must name a live thread of the caller's process, otherwise the caller takes the lock with `EOWNERDEAD`; each thread keeps a list of the PI words it owns with waiters, and its exit wakes them (so they get `EOWNERDEAD`). The key is (process, address): private only, since shared mappings arrive in phase 6. The wait table holds one entry per blocked task, so it is `MAX_TASKS` long and never full. A deadline is the kernel's only sleep: each core caches its earliest deadline and rearms its timer only when that moves earlier (a late fire just rechecks), so neither the switch path nor `yield` scans the table or writes the timer. `thread_exit` gains musl's clear-tid-and-wake (a tid address given to `thread`, zeroed and woken at exit) and a new `unmap` call frees pages (musl's detached threads unmap their own stack); it skips pages not present (a sibling's chunked `map` may not have reached them, or another `unmap` took them) and refunds the charge of pages reserved but not yet mapped, so it never frees `PhysAddr(0)` or walks a missing table. | 28 | Per-CPU run queues, wake preemption | Each core gets its own run queue: one index list per priority level, linked through the task table (no heap), so `advance` costs the number of levels, not a scan of every slot; blocked tasks hang on per-event lists, so `wake(event)` touches only its waiters; free slots are a free list. Placement is deterministic, with no heuristics: a woken task goes to the core it last ran on; if that core runs an equal or higher priority and another core idles, to the lowest-numbered idle core (an idle bitmap, one bit per core, sized at boot and scanned a word at a time). A woken task that outranks its core's current task preempts it at once, locally by switching or remotely by the reschedule SGI (phase 3's "a wake does not preempt yet" ends here; 25b already wakes idle cores). An idle core pulls one task before `wfi`, from the lowest-numbered core in an overloaded bitmap (cores with a task waiting, scanned a word at a time), so a pull reads N/64 words, not every core's queue. | 29 | Fair class (EEVDF) | Levels 1-3 stay the strict-priority RT class with PI; level 0 becomes the fair class, scheduled per core by EEVDF: each task has a weight (1024 by default) and a virtual runtime; a task is eligible when its lag is not negative, and the eligible task with the earliest virtual deadline (vruntime + slice * 1024 / weight) runs. Vruntimes are kept relative to the queue's minimum vruntime, so the weighted average cannot overflow. Runtime is charged from `CNTVCT_EL0` at each switch and tick; a sleeper keeps its lag, clamped to one slice; a pulled task keeps its lag against the new core's virtual time; `yield` moves the task's deadline one slice on, so two yielding tasks still alternate (`test=yield`). One base slice constant (about 3 ms), no tunables; the slice end joins step 27's cached earliest event, and the timer is rearmed only when that moves earlier (a yield's new slice end is always later, so yield pays nothing). The pick is indexed, since step 31 bounds tasks only by RAM: each core's fair tasks sit in an augmented balanced tree keyed by vruntime whose nodes cache their subtree's earliest deadline (Linux's EEVDF form), linked through the task table (no heap), so pick, insert and remove are O(log n). RT always beats fair, and PI lifts a fair owner to its waiter's RT level. Boot-spawned programs keep the top RT level (the tests rely on it) except the shell init (`msh`, busybox), which starts fair, so typed commands share the CPU fairly. e2e `test=fair` (`-smp 1`, or the hogs just take separate cores): two kernel hogs at weights 2048 and 1024 split one second 2:1 within 5% (from the scheduler's runtime accounting); beside four hogs, a task waking every 2 ms (`futex_wait` deadline) is picked at its wake while its lag stays within one slice plus the largest single charge; an RT task is picked at its wake ahead of the fair hogs (both asserted on scheduler state). Host tests: eligibility, deadline order, lag kept and clamped across sleep, lag kept across a pull, ties broken by slot, no overflow at the largest task table (RAM / 16 KiB, 196608 tasks at the 3 GiB cap) of maximum weight, or the bound shown with `i128` arithmetic, tree pick against a linear scan on random sequences. Benchmarks: yield, syscall, pipe, boot hold: `test=bench`'s kernel tasks (level 0) now run fair, so yield gates the fair pick, and syscall and pipe (top RT level) gate the RT path. Keeps: RT before fair; one-level PI; determinism (same inputs, same order). |
| 30 | Resource groups | A group is a kernel object reached by a handle (fixed table `Groups<G>`, entries by index and generation like pipes): a CPU weight (the group is one entity in each core's fair queue and its tasks share its time; groups do not nest), a CPU bandwidth (quota per period, a token bucket refilled each period; an overrun carries into the next period, so tokens can go negative and the long-run share holds; a group out of tokens has its fair tasks off the queues until the refill), a task cap (live threads, counted at `spawn` and `thread`; over the cap is `EAGAIN`), and a frame budget (decided by the user: a child spawned without an explicit budget, `budget` 0, charges its group's budget directly, like a cgroup, with no frames moved; an explicit budget still moves that many frames into a budget of the child's own, which caps it, as today; a process's `Memory` names the budget it charges, its own or its group's, so a charge stays one compare and add). ## Decided

- **No practical core cap** (approved by the user, 2026-10-07: "we need to support as many cores as possible"): steps 25b-25c, 28-30 (per-core run queues, the per-core fair pick and group accounting are the real scaling work) and 32. Each per-core cost takes its cheapest safe form: GICv3 only, a dense index from the DTB, per-CPU areas sized at boot behind TPIDR_EL1, tree bring-up, a queued lock. Measured on this host (Apple M4 Pro, 12 cores: 8 performance, 4 efficiency; QEMU 9.2.1), with `-cpu cortex-a72`:
  - QEMU `virt`: GICv2 takes at most 8 cores; GICv3 at most 512 (TCG).
  - hvf with GICv3: QEMU starts at most 64 vCPUs (`HV_NO_RESOURCES` at 65). A guest using the trapped ICC registers is unverified until step 25c's first test. `-cpu host` fails on this M4 (`host-arm-cpu.sme` not found), so `-cpu cortex-a72` stays.
  - So hvf benchmarks scale over 1-12 cores (more vCPUs than host cores are overcommitted), and 64, 128 and 512 cores are TCG correctness runs (user, 2026-10-07).
- **GICv2 is deleted** in 25c (user, 2026-10-07): GICv3 only, as QEMU `virt` is the only supported board. If phase 11 picks a Raspberry Pi (4 and 5 use the GICv2 GIC-400), the driver is restored from history then.
- **A child without an explicit budget charges its parent's group** (user, 2026-10-07; steps 30-31): like a cgroup, the group's frame budget is shared by its budget-0 processes, and an explicit budget still caps a child. libc spawns with budget 0.
- **No fixed limits** (approved by the user, 2026-10-07): step 31. Any object's limit is its owner's budget; system tables are sized at boot from RAM and per-process tables grow in charged frames. - **Kernel stack guard pages wait for phase 6** (user, 2026-10-07): in the 1 GiB identity block a guard page means splitting the RAM block into page tables; phase 6's higher-half kernel maps stacks page by page anyway and gives task kernel stacks guards at the same time.

## Notes

- Kernel code still never preempts itself: a trap runs to completion under the big lock, so the bounded-work rules (`MAX_BUFFER`, `MAX_MAP`, the path and `readdir` limits until step 31; from step 31 `CHUNK`, the 16-component walk chunk and its named exceptions) now also bound how long other cores wait. A `sync` holds the lock for its flushes (about 137 us); phase 7's async block path removes that, or step 32 splits the file system out.
- `Lock<T>` and `PerCpu<T>` live in `arch` because `UnsafeCell` access needs `unsafe`; the kernel crate stays lock-free data behind the board, so its host tests need no lock.
- AArch64 broadcasts inner-shareable TLB and icache maintenance in hardware, so the SGI exists only for waking and rescheduling cores (idle wake, kill, wake preemption), never for shootdown.
- What phase 6 needs from this model: the probe-then-access helpers (`at s1e0r/w`) return `EFAULT` on a page not yet present (demand paging) or copy-on-write (the futex CAS), so kernel user access becomes fault-in-and-retry (or an exception fixup); and a page-in must never run under `KERNEL`, or every core stalls for the disk.
- A chunked call's frame holds advanced x2-x4 between chunks, so the exception channel and libc-built signals (later phases) deliver only at a call's final return, or restore x2-x4 from the task slot before delivering.
- MogFS v1's limits (`MAX_BLOCKS`, `MAX_INODES`, `MAX_FILE_SIZE`) and the virtio queue depth are phase 7's.
- Shared-memory futexes (keyed by frame), `wait_many`, an affinity API, scheduling domains, nested groups, signals and the exception channel are later phases.
