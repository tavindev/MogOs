# Phase 4: Shell and Storage

Goal (milestone): from a shell on the console, `ls`, `mkdir`, create a file, write to it, and save; after a reboot on the same disk image, the directory and file contents are still there. POSIX userland (musl, busybox) follows the milestone.

## Steps

Steps 18, 20 and 21 are independent and run in parallel; 22 integrates them.

| # | Step | Done when |
| --- | --- | --- |
| 18 | Console input | GIC SPI enabled for the UART; UART receive with a minimal line discipline (echo, backspace, line delivered on Enter). A blocking `io_submit_wait` read on the console handle returns one line. The e2e harness writes to QEMU's stdin and asserts the echoed line and what the program read. |
| 20 | virtio-blk | virtio-blk over virtio-mmio (found in the DTB; legacy vs modern pinned after checking QEMU's default) reads, writes and flushes 4 KiB blocks. Kernel-internal block API (no user handle yet). e2e: boot with a disk image, write a block, flush, reboot, read it back. Throughput benchmark recorded. |
| 21 | MogFS crate | A safe, `no_std` crate over a `Disk` trait (read/write/flush 4 KiB blocks), shared by the kernel and a host `mkfs`. Copy-on-write: every change writes new blocks; `commit` flushes, writes the next superblock (two alternating slots, generation + checksum), flushes. Checksums on every block; a bad block reads as an error. Operations: lookup, readdir, mkdir, create, read, write (whole-file or append is enough), commit. Host-tested with an in-memory disk: round trip, corruption detected, power cut at every write of a commit leaves the old or the new state, never a mix. |
| 22 | Files + native shell (milestone) | Kernel file objects with MogFS and the boot archive behind one interface: `open(dir, name, flags)` (create), `mkdir(dir, name)`, `readdir`, read/write through `io_submit_wait`, `sync` (commit). `..` and absolute paths cannot escape a directory handle. A tiny native shell (`msh`, `crates/user`) with `ls`, `mkdir`, `touch`, `write <file> <text>`, `cat`, `sync`. e2e: boot 1 runs `mkdir docs`, `write docs/a.txt hello`, `sync`; boot 2 on the same image runs `ls docs` and `cat docs/a.txt` and sees `a.txt` and `hello`. |
| 23 | musl + busybox | musl's `syscall_arch.h` replaced by a dispatcher from Linux syscall numbers to native calls (anything else returns `-ENOSYS`); the fd table is a libc map over handles; stdin/stdout/stderr are fixed handle slots at spawn. `posix_spawn`/`vfork` map to native spawn; `fork` returns `ENOSYS` for now. Signals: `^C` kills the foreground child through its process handle; `SIGCHLD` comes through `wait`; others are ignored. busybox (no-fork configuration, to verify) runs `sh`, `ls`, `cat`. Needs a C cross toolchain on macOS. |

## Notes

- The filesystem lives in the kernel (monolithic), behind the file-object interface. MogFS logic is a pure crate so it is host-tested without QEMU.
- `msh` exists to reach the milestone without a libc port; busybox replaces it as the default shell in step 23.
- A shared-memory submission ring is a later optimization of step 15's completion path, only if its benchmark justifies it.
- Linux binary compatibility comes after this phase (see ROADMAP).

## What was done

Filled in as each step lands.

- Step 20: virtio-blk over modern (version 2) virtio-mmio. QEMU 9.2 defaults the transport to legacy, so the runners and e2e pass `-global virtio-mmio.force-legacy=false`; modern takes three 64-bit queue addresses where legacy needs a page-size register and one page-aligned ring block, and a legacy transport reads as no disk. `Dtb::virtio_mmio` walks every `virtio,mmio` node (`reg_of` now takes a callback, called once per matching node), and the board's `VirtioBlk::new` probes each for magic, version 2 and device ID 2, requires `VIRTIO_BLK_F_FLUSH` (QEMU keeps its write cache only when it is negotiated) and negotiates it with `VIRTIO_F_VERSION_1`, then sets up one 4-entry split queue in one frame from the frame allocator (descriptors, available and used rings, request header and status), after `init_frames`. Every request is the same chain at descriptor 0 (header, data, status; a flush skips the data), so the zeroed available ring never changes, only its index; the device is told not to interrupt (`VIRTQ_AVAIL_F_NO_INTERRUPT`) and the driver polls the used index: one request in flight, synchronous calls, one MMIO exit (the notify) per request (interrupt completion waits for the GIC SPI work). The kernel's block API is `kernel::Disk`: `read(block, &mut [[u8; BLOCK]])`, `write(block, &[[u8; BLOCK]])` (`BLOCK` = 4096; any number of consecutive blocks in one request) and `flush`, each `Result<(), i64>`; `Board::disk(&dtb)` returns the board's implementation. The device moves data straight to and from the caller's blocks (no bounce copy): the driver accepts only buffers inside the identity-mapped RAM GiB, where every kernel buffer's virtual address is its physical one, and returns `EFAULT` otherwise (a user-space address never reaches DMA); a failed request or an overflowing block number is `EIO` (-5, new); an empty read or write does nothing (QEMU fails one). `run` prints `disk: found` or `disk: none` after the `boot:` line, so probing the 32 transports does not count toward boot time. No user handle yet. `test=disk`: reads blocks 1-2 in one request; if they hold the test pattern, prints `disk: read ok`, otherwise writes them in one request, flushes and prints `disk: wrote` (empty reads and writes are checked too). e2e boots twice on one zeroed temp image (`wrote`, then `read ok`) and checks bytes 4096..12288 of the image on the host, so a block-to-sector mix-up fails; the plain boot test asserts `disk: none`. Same lines under hvf. `test=bench-disk` writes 2048 sequential blocks (8 MiB) and flushes, then reads them back, at 4 KiB and then 256 KiB per request. Speed work: zero-copy DMA (the bounce copy was about 0.5% of a 4 KiB request), one exit per request, multi-block requests (hvf 256 KiB: 3415 MiB/s write+flush, 8629 read, against 148 and 188 at 4 KiB; QEMU's per-request host work, about 20 us, bounds the 4 KiB case, so batching is the lever), and `-global virtio-mmio.ioeventfd=off` (QEMU handles the notify in the vCPU thread: 4 KiB +9% write, +19% read, 21 interleaved hvf boots). Not done: several scattered requests in flight (needs a submit/complete API, best with interrupts) and `VIRTIO_RING_F_EVENT_IDX` (only helps with several in flight). hvf medians, 63 interleaved boots vs `63591f4`: yield 70/70 ns, syscall 29/29 ns, pipe 378/379 ns, boot 203/205 us (noise). `crates/user/Cargo.toml` gets an empty `[workspace]` so the board's nested user build works from a worktree under the main checkout. Step 21/22: MogFS defines its own `Disk` trait; integration picks one (MogFS cannot depend on `kernel`, so likely MogFS's, implemented for `VirtioBlk`).
